## 二、大屏为什么没有用 go-view

`docs/spec_tickets` 时代定的方案是「go-view 大屏接 StarRocks ADS」，实测走不通，原因是**本机的 go-view 只有半套**：

1. `D:/starrocks/go-view/dist` 是前端静态产物，编辑器登录要调 `go-view-server`（Go 后端）的 `/api/login`，这个后端从没部署过；
2. 打开 `http://localhost:8080` 直接被重定向到 `#/login`，没有凭证进不去编辑器；
3. `go-view-server` 官方只发 GitHub Release，本机拉不到（直连 502、镜像源无此包）。

结论：**容器里是一个进不去的空壳**。于是改成 DataPilot 自建大屏页（React + 手写 SVG，零新依赖），继续复用 8080 端口 —— 换成 `dp-web` 容器托管前端 dist 并反代后端，go-view 容器停掉保留（`platform-ui-compose.yml` 里注释掉整段，写明恢复条件）。

这个替换的代价和收益都写清楚：**少了 go-view 的拖拽编排能力**（以后要加新图要改代码），**换来的是可测、可截图、可进 Git 的看板**，以及零前端依赖 —— 本机 npm 装 echarts 也不一定拉得动（同一批网络问题）。

## 三、监控栈组成

```
Prometheus (9090)  ←─ node-exporter (9100)          宿主机 CPU/内存/磁盘
                   ←─ kafka-exporter  (9308)          broker / topic
                   ←─ sr-ai-analysis:8030 /metrics    StarRocks FE
                   ←─ sr-ai-analysis:8040 /metrics    StarRocks BE
                   ←─ flink-jobmanager:9249           Flink JM（内置 prometheus reporter）
                   ←─ flink-taskmanager:9249          Flink TM
Grafana (3000)     ←─ Prometheus（provisioning 数据源 uid=prometheus）
```

配置文件全部进 Git：`deploy/monitoring-compose.yml`、`deploy/monitoring/prometheus.yml`、`deploy/grafana/provisioning/**`、`deploy/grafana/dashboards/datapilot-overview.json`。改面板 = 改 JSON + 重启 grafana 容器，不靠 UI 手点。

**cadvisor 暂缺**：官方镜像只在 `gcr.io`，本机 gcr 直连超时、daocloud 对 gcr 转发 403、1ms/rat.dev 两个源 DNS 不通、Docker Hub 上 `cadvisor/cadvisor` 404。少的只是「容器级 CPU/内存」一块，链路指标不受影响。`monitoring-compose.yml` 与 `prometheus.yml` 里都留了注释掉的完整配置，镜像能拉通时取消注释即可。

## 四、踩的五个坑

1. **node-exporter 不能带 `rslave`**：Windows Docker Desktop 报 `path / is mounted on / but it is not a shared or slave mount`，去掉 `rslave` 才能起。也因此它看到的是 Docker 的 Linux VM，不是 Windows 的 C/D 盘 —— 面板里「Docker 磁盘使用率」抓的是 `/mnt/docker-desktop-disk`，不是 C 盘。

2. **Flink reporter 的配置方式**：不用改 `flink-conf.yaml`，在 compose 的 `FLINK_PROPERTIES` 里加两行即可（`metrics.reporter.prom.factory.class` + `metrics.reporter.prom.port: 9249`），JM/TM 都要加。

3. **重建 Flink 容器会丢容器内的 jar**：原来的 starrocks connector 是 `docker cp` 进容器的，没进 compose 的 volumes，容器一重建 job5 就 `Cannot load user class: StarRocksDynamicSinkFunctionV2`。补进 volumes 后又遇到 **`InvalidClassException: StreamLoadManagerV2` —— 原因是版本不一致**：Dinky 侧提交用的是它自带的 `1.2.14_flink-1.20`，Flink 侧我挂的是从 Maven 下的 `1.2.9_flink-1.18`，作业图在 Dinky 侧序列化、在 TM 侧反序列化时 serialVersionUID 对不上。**结论：两端的 connector jar 必须完全同版本同 md5**，直接从 Dinky 容器 `docker cp` 出来挂给 Flink。

4. **作业重复提交会让数据翻倍**：调试 job5 期间反复重启全链路，Paimon 的 `ods_orders` 是 append 表，每次 job1 全量重放都追加一份 → DWS 聚合把同一批订单累加了 5 次，SR 的 GMV 从 53042.41 变成 265212.05（正好 5 倍）。修复流程：取消作业 → 把湖里 ODS/DWD/DWS 目录 `mv` 到 `/paimon_warehouse_bad_20261021/`（没删）→ HMS 里的表记录还在会让 `CREATE TABLE IF NOT EXISTS` 跳过，所以还要 `DROP DATABASE mall_dw CASCADE`（`deploy/sql/zz_maint_drop_mall_dw.sql`）→ 按 job2→job3→job4→job5 顺序重建 → job6 全量重建 SR。**教训：流作业重启前先想清楚「这段数据会不会被重放一次」。**

5. **Grafana 13 的 panel 容器 testid 变了**：`[data-testid="panel"]` 选不到，验收脚本改成按面板标题文本判定 —— 反正标题才是人看得见的东西。

## 六、已知边界

- 大屏匿名可读（只放聚合数据），写接口仍需角色；跨域只放开 `localhost/127.0.0.1` 任意端口，外部来源 403。
- 大屏数据靠 30 秒轮询，不是 WebSocket 推送 —— ADS 本身就是流式写入，轮询足够，且省掉一条长连接。
- 后端没容器化：`8080` 的 `/api` 反代指向宿主机 `18080`，**后端没起时大屏会显示「数据加载失败」**。要常驻得单独起 `mvn spring-boot:run`（或后续把后端也塞进 compose）。
- node-exporter 看到的是 Docker 的 Linux VM，宿主机 Windows 的 C/D 盘用量不在监控里。
- cadvisor 缺失，容器级内存/CPU 暂无法按容器拆分。
