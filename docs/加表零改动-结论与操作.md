# 加一张表需要改代码吗？（Ticket 19 结论与操作手册）

> 结论先说：**不需要改代码**，但这句话在 Ticket 19 之前并不成立。
> 独立评审逐个链路核过源码后找到 4 处会让它不成立的地方，其中 1 处是真硬编码。
> 本文记录这 4 处的现状、修法、剩余边界，以及「加一张表」的完整操作路径。

## 一、逐链路的判定（评审结论 + 本轮修复）

| 链路 | 加表/减表要改代码吗 | 依据 |
|---|---|---|
| 闸门①存在性 / ②权限 | 不需要 | 只读 `OntologyCache.tables()/fields()`，缓存来自 `semantic_model`，60s TTL + `MetadataChangedEvent` 立即失效 |
| 闸门③语法 | 不需要 | `SqlValidator` 用同一份缓存做二次比对 |
| SQL 生成 | 不需要 | 表名取自 `metric.getTableName()`，维度选表靠 `dimensionTables()` 反查 |
| 意图召回 | 不需要 | `Recaller` 从 `repo.listTables()` 动态取全量表 |
| 前端元数据页 | 不需要 | 全部由 `api.tables()/api.fields()` 渲染 |
| **引擎白名单自检** | ~~需要改~~ → **已改成不需要** | 见缺口 1 |
| 经营大屏 | **需要改（设计如此）** | 见缺口 2 |
| 元数据写入 | ~~只能手工 INSERT~~ → **已有接口** | 见缺口 3 |
| 新环境重建 | ~~漏表~~ → **有导出脚本** | 见缺口 4 |

## 二、四个缺口

### 缺口 1（已修，P1）：引擎声明表的硬编码

**原状**：`sql/StarRocksSqlExecutor.java` 里

```java
private static final List<String> DECLARED = List.of(
        "ads_trade_overview_di", "ads_channel_conversion_di",
        "ads_region_gmv_di", "ads_product_sales_rank_di");
```

`EngineWhitelist.effective()` 取的是 `DECLARED ∩ semantic_model`：加第 5 张表后交集里永远没有它，
`GET /api/health/engine` 立刻返回 `consistent=false`，启动日志多一条 `metadataNotDeclared` 的 warn。
它**不拦截问数**（`EngineWhitelist` 只被 `HealthController` 引用），但运维看到红点会以为链路坏了，
于是回来改代码 —— 恰好和「加表零改动」相反。

**修法**：
1. `DECLARED` 改为空（`List.of()`）。空集合的语义本来就写在 `EngineWhitelist` 注释里：
   「引擎没声明 = 不额外限制，纯元数据说了算」。
2. 修 `EngineWhitelist.report()` 的一个真 bug：原来无条件做 `metadata - declared`，
   `declared` 为空时它恒等于**全部元数据** → `consistent` 恒 `false` + 每次启动 4 条 warn。
   现在未声明时 `metadataNotDeclared` 为空，并新增 `declarationMode=metadata-only` 字段说明当前模式。
3. 启动日志多打一行：`引擎未声明表清单，可读集合完全由元数据决定（加表无需改代码；物理一致性看 /api/health/drift）`。

**物理一致性交给谁**：`SchemaDrift` 查 `information_schema` 出 `inDbNotInOntology / inOntologyNotInDb`，
比静态清单准（加表后、灌数前它会报 `inOntologyNotInDb`，这是**预期**告警，说明元数据先于物理表就位）。

**回归点**：`qa/verify_metadata_table.py` 第 ⑩ 段断言加表后 `consistent=true`、`declarationMode=metadata-only`。

### 缺口 2（记录边界，P2）：经营大屏是固定口径视图

`dashboard/DashboardService.java` 里有 4 个表名常量（`mall_dw.ads_*`），SQL 里的列名也是写死的；
前端 `DashboardPage.jsx` 固定渲染渠道/地区/商品三个面板。

**这不是缺陷，是定位**：大屏是「按业务定制的一块看板」，不是「元数据驱动的问数」。
加表后大屏不呈现**符合预期**。若将来要元数据驱动的大屏，那是另一个功能（配置化的面板定义），
不要拿「加表零改动」去验收大屏 —— 那一轮必然判不通过，而且是误判。

### 缺口 3（已修，P2）：元数据只有读接口，加表要手工 INSERT

**原状**：`MetadataController` 只有 `GET /api/metadata/tables`，没有写接口。
加表只能连 MySQL 敲 `INSERT INTO semantic_model` —— 那不是改代码，但也不是产品能力：
它绕过 `write-enabled` 急停、绕过鉴权（admin/dba）、不进审计。

**现在的接口**（鉴权与字段一致：admin 或 dba；`write-enabled=false` 时 403）：

```bash
# 注册（mode=create 已存在 → 409；默认 upsert 覆盖注释/业务域）
curl -u admin:Admin@2026 -X PUT 'http://localhost:8080/api/metadata/tables?mode=create' \
  -H 'Content-Type: application/json' \
  -d '{"tableName":"ads_new_overview_di","tableComment":"新渠道总览","bizDomain":"渠道"}'

# 注销（五类引用任一存在 → 400，并说清是谁在用）
curl -u admin:Admin@2026 -X DELETE \
  'http://localhost:8080/api/metadata/tables?tableName=ads_new_overview_di'
```

**注销前的五道守卫**（任一命中就 400，**不做级联删除**）：

1. `field_metadata` 里还有该表字段 → 要求先逐个摘（一次删二十几行，出问题无法回退）
2. `metric_def.table_name` 还把该表当主表 → 点名是哪些 `metric_id`
3. `metric_def.denominator_table` 把它当分母表 → 点名（`gmv_channel_ratio` 这条跨表链）
4. `dimension_def.table_name` 还绑着它 → 列出维度名
5. `metric_table` 关联里还挂着 → 列出指标

为什么不做级联：任一处漏删，问数时的报错都是「指标关联的表不在白名单」（闸门①），
而真实原因是「有人把表注销了」—— 没人反推得出来。拒绝并要求先清引用，排查路径只有一条。

**页面**：元数据页左侧表卡片新增「新增表」按钮与每行「注销」，行为与接口一致。

### 缺口 4（已修，P3）：seed 只覆盖基线，新环境重建会漏表

`deploy/seed.sql` 是手写基线（4 表 / 28 字段 / 13 指标 / 5 条阈值）。
它对 `semantic_model`/`field_metadata` 用 `INSERT IGNORE`（**只补缺、不删新增**），
所以「重跑 seed 会清空新表」这个说法不成立；真正的问题是**它不反映实况**：
新环境如果只跑 seed，后加的表就丢了，`/api/health/drift` 立刻报 `inDbNotInOntology`。

**新增导出脚本**：

```bash
python qa/dump_metadata.py http://127.0.0.1:18080 -o deploy/seed_from_live.sql
# 幂等：semantic_model / field_metadata 用 INSERT IGNORE（不覆盖人工改过的注释）
#       metric_def / gate_config 用 ON DUPLICATE KEY UPDATE（口径以导出文件为准）
mysql -h127.0.0.1 -P3307 -uroot -proot123 data_agent --default-character-set=utf8mb4 < deploy/seed_from_live.sql
```

实测：导出 4 表 / 28 字段 / 13 指标 / 5 阈值，重放一遍计数不变（`metric_table` 17 行），中文与枚举值无损。

**顺带发现的一处漂移**（如实记录，未修）：`ads_trade_overview_di.dt` 在活库里 `field_role` 是 `NULL`，
而 `seed.sql` 写的是 `dimension`。说明活库被页面改过、seed 没跟上 —— 这正是「导出比 seed 可信」的实证。

## 三、加一张表的完整操作路径

```
1. 物理表就位（StarRocks 里 CREATE TABLE，或 Flink/Paimon 同步建好）
2. 元数据注册        PUT /api/metadata/tables?mode=create      ← 页面「新增表」
3. 字段白名单        PUT /api/metadata/fields?mode=create ×N   ← 页面「新增字段」
4. 指标口径          PUT /api/metrics                          ← 指标页（复用已有指标可跳过）
5. 维度字典（可选）  SQL 插入 dimension_def                     ← 目前仍无接口，见「剩余缺口」
6. 自检              GET /api/health/metadata / /api/health/engine / /api/health/drift
```

第 1~4 步全部有接口或页面，**不需要改代码**。第 5 步（`dimension_def`）目前仍要写库，
它不影响「能不能问这张表」，只影响「能不能按这个业务维度问」。

## 四、剩余缺口（如实挂账）

| 项 | 影响 | 现状 |
|---|---|---|
| `dimension_def` 无写接口 | 新增业务维度要手工 INSERT | 挂账；不影响加表主链路 |
| 大屏固定口径 | 新表不会自动出现在大屏 | 设计如此，见缺口 2 |
| Milvus few-shot 索引 | 启用向量召回后，加表要重建 embedding | 挂账（当前未启用 Milvus） |
| AskPage 示例问题硬编码 | 新表的示例问法不会自动出现 | 挂账，属易用性 |
| `denominator_table` 索引 | 删表守卫已覆盖；但 `metric_table` 需人工同步 | 已由导出脚本派生，接口侧无自动维护 |

## 五、怎么验

```bash
# 端到端：注册 → 加字段 → 删表被挡 → 摘字段 → 删表成功 → 清单消失（23 项）
python qa/verify_metadata_table.py http://127.0.0.1:18080

# 单测：四类引用 + 字段守卫 + 409 + 404（10 例）
mvn -o test -Dtest=MetadataServiceTableTest

# 引擎自检不再误报（3 例）
mvn -o test -Dtest=EngineWhitelistTest
```

Ticket 19 实测：`verify_metadata_table` 23/23、`MetadataServiceTableTest` 10/10、
`EngineWhitelistTest` 7/7、前端冒烟 42/42（含「新增表」入口与弹窗）。
