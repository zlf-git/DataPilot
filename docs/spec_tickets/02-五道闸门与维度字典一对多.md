## 交接（来自 Ticket 07）

- `EngineWhitelist.isReadable(table)` 由本票的存在性闸门消费：判「表在引擎侧可不可读」时用它（引擎声明 ∩ 元数据白名单），不要只查 `OntologyCache.tables()`，也别把它当死代码删掉（QA-07 P2-3）。

### 追加验收项（来自 Ticket 07 二审，2026-10-21）

**闸门③ 必须用「引擎 ∪ 元数据」的交集判可读，不能只看元数据白名单。**

- 现状（07c 实测）：`datapilot.engine.type=mysql` 时引擎只声明 `orders`，元数据白名单仍是 4 张 ADS，`EngineWhitelist.effective()` = ∅。此时问 ADS 问题，闸门③ 全 PASS，**到 JDBC 层才抛「表不存在」** —— 错误暴露得太晚，且用户拿到的是一句 SQL 异常而不是「你问的表当前引擎读不到」。
- 验收：
  1. 闸门③ 判表可读改用 `EngineWhitelist.isReadable(table)`（= `declared ∩ metadata`）；
  2. `effective` 为空时在 IR 层直接 reject，文案可执行：「当前引擎 {type} 无可读表，请检查语义层与 datapilot.engine.type 是否匹配」；
  3. 两条用例各一：① StarRocks 模式下四张 ADS 表仍 PASS（零回归）；② MySQL 模式下问 ADS 表在闸门③ 被 reject、且 `stage=IR`；
  4. 若判断为「元数据白名单本就该按引擎分库」，把语义层改造一起做（归 Ticket 15/16），不在本票半改。
- 交叉引用：`07-引擎接口化.md` §07c「未接线」。

### 追加验收项 2（来自 Ticket 09 埋点实测，2026-10-21）

**维度/过滤字段必须校验「是否属于本次查询的表」，不能只查全局字段白名单。**

- 现状（09 实测）：问「反例：按渠道名称看总GMV」时，IR 里 `dimension=channel_name`，闸门① 判 `channel_name` 在全局字段白名单里（它确实属于 `ads_channel_conversion_di`）→ **放行**；随后 `IrToSqlConverter` 按表隔离才拒绝。用户看到的文案是对的，但拒绝发生在转换期而非闸门期。
- 连带影响：`agent_run.status` 把这类运行记成 `FAILED` 而不是 `REJECTED`，「拦截率」按 `REJECTED` 统计会漏算这一类。
- 验收：
  1. 闸门① 的维度/过滤/排序字段校验改为「字段 ∈ 本次查询主表（或显式声明的表）的字段集」，不只看全局白名单；
  2. 拒绝文案保留表级信息（现有「维度字段 X 不属于表 Y」的文案已经是好文案，直接复用）；
  3. 用例：跨表维度在闸门① 被 reject、`stage=IR`、`agent_run.status=REJECTED`；
  4. 与「追加验收项 1」（引擎可读表）同一批做，两处都是「白名单只有全局一份」的后果。
- 交叉引用：`09-AgentOps埋点.md` §落地记录「本票暴露、不属本票范围」。
