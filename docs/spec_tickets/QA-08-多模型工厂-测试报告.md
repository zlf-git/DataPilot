## 6. 修复建议

1. **P2-1 + P2-3 同一条规则一起收口：「空值 = 默认值」必须由装配侧决定，不能由 `EngineJdbc`/`LlmClientFactory` 单方面归一**。
   - `StubLlmClient` 的 `@ConditionalOnProperty(..., havingValue="stub", matchIfMissing=true)`，同时 `RealLlmProviderCondition` 对空值返回 false —— 两边就对齐了，空值与缺省都落到桩。
   - 引擎侧同理：把「取值归一」抽成一处（如 `EngineType.normalize(raw)`），`@ConditionalOnProperty` 换成 `@Conditional` 调用同一个函数，`EngineJdbc` 也调它。`engine.type=` 与「删掉这行」才会走同一条路。
2. **P2-2**：`/api/health/llm` 的 `client == null` 分支要么删掉（承认不可达），要么改成 `@ConditionalOnMissingBean` 之外的显式探针；保留一段永远跑不到的「兜底代码」会让人误以为它被测过。
3. **P2-4**：补一例 `cfg.setApiKey("sk-config") + env(DEEPSEEK_API_KEY="sk-env") → 期望 sk-config`。这一条是「Key 只走环境变量链」的安全边界，配错方向会让 yml 里的显式值被环境变量静默覆盖。
4. **P2-5**：在 `LlmGeneration` 上加一个来源标记（`usageFrom`：`stub` / `provider`），或者让桩的 token 返回 `0`。否则 Ticket 09 上线后，离线评测会产出一张「每问 600 token」的成本表，而这个数字是常量。
5. **P2-6**：把 `stubDoesNotWireRealClient` 挪到含 `StubLlmClient` 的上下文里，断言 `hasSingleBean` 且类型是 `StubLlmClient`；顺带覆盖 `provider=deepseek` 时容器里**没有**桩。
6. **P2-7**：`normalizeBaseUrl` 的 `while` 改成 `if`（只剥一层），或对 `.../v1/v1` 记一条 warn —— 「用户写了两个 v1」更像配置错，静默修正会掩盖问题。
