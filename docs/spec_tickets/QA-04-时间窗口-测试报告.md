### 3.3 锚点缓存（TCP 连接计数代理实测）

方法：JDBC 未池化（`DriverManagerDataSource`），**每次查询 = 一条 TCP 连接**，所以用代理 19030 统计到 9030 的连接数就能数出「查了几次库」。

| 场景 | 新增连接 | 解读 |
|---|---|---|
| 第 1 次 Q2（冷缓存） | **5** | 1 次执行 + 4 次锚点预热（RecallStep 对 4 张候选表 `prefetchQuietly`） |
| 连打 4 次 Q2 | **4**（每次 1） | 锚点全部命中缓存，只剩执行 |
| 换 Q11（另一张表） | **1** | `ads_channel_conversion_di` 的锚点已在首次预热里缓存 |
| 空闲 62s 后打 1 次 | **5** | TTL 60s 到期，锚点重查 → **TTL 真实生效** |
| TTL 到期后 8 并发 | **12** = 8 执行 + 4 锚点 | 无缓存击穿（虽然 `getIfPresent`+`put` 非原子，实测未放大） |

结论：交付声明的「一次问数只查一次库」应精确表述为**「每张表每 60s 最多查一次」**——首次问数会为召回出的每张候选表各查一次。

## 四、缺陷清单

### P1-1（03 遗留，本票未修）空问题静默返回 Q1 的数据

`{"question":""}` 与 `{"question":" "}` 都返回 `WHERE dt = ?` + `53042.41`、`answer=""`。属第 4 类静默错（看着成功，实则答非所问）。根因仍是 `StubLlmClient.extractQuestion` 取到空串时回落整段 prompt，而 prompt 里的 few-shot 正文就是 Q1 原题。
位置：`llm/StubLlmClient.java` extractQuestion、`agent/AgentEngine.java` 入口。
（`"\n"` 与「今天天气怎么样」正常返回「无法识别」，只有空串/单空格中招。）

### P1-2（评测判据失效）「不取 8 天」在现有数据上不可判别

`2026-10-12` 在四张 ADS 表里均为空分区，导致：
- `BETWEEN '2026-10-12' AND '2026-10-19'`（闭区间、8 天）与 `dt > '2026-10-12' AND dt <= '2026-10-19'`（半开、7 天）**返回值逐题相同**（Q2 69、Q11 138821.73、Q12 254466.85、Q13 293469.91）。
- 于是「结果 7 行、不取 8 天」这条验收**只对被实现的 SQL 形状敏感，对结果值不敏感**。若哪天有人把 `buildTimeRange` 改回 BETWEEN，`e2e_stub.py` 还能靠 `sqlMust: ["dt > ?"]` 拦住，但任何「只看值」的评测（人工目测、只做行级对拍的 06b）都会**放行**。
建议：06b 把「窗口题必须断言 SQL 形状」写成硬规则；或把 days=3 这类探针纳入回归（days=3 下半开与闭区间差 66184.50，可判）。

### P2-1 relativeWindow 缺失时静默按 LAST_N_DAYS 处理

`buildTimeRange` 第 266 行 `tr.getRelativeWindow() == null ? "LAST_N_DAYS" : ...`，与 `TimeRange.java` 注释「其余取值生成器显式拒绝，**不做猜测**」自相矛盾。真实 LLM 漏填 `relativeWindow` 时会被当成「近 N 天」静默放行，`days` 是唯一约束。

### P2-2 锚点缓存非原子 + 无连接池

`TimeAnchorProvider.anchor()` 是 `getIfPresent` → `loadAnchor` → `put` 三步，冷缓存并发理论上会重复查库（本次 8 并发实测未放大，属运气+请求够快）。Caffeine 有原子写法 `anchors.get(key, this::loadAnchor)`。另外它自建 `DriverManagerDataSource` 无池化，每条锚点查询新建 TCP 连接（实测可见）。

### P2-3 TTL 60s 硬编码

其余闸门参数都在 `gate_config` 里可热改，唯独锚点 TTL 写死。数据日更的场景 60s 合理，但没有留口子。

### P2-4 anchor 比对是字符串严格相等，无格式归一

IR 给 `"2026-10-19 "` 能靠 `trim()` 救，但给 `"20261019"`、`"2026/10/19"` 一律判「与数据最新日不一致」。语义上它其实是对的（格式非法就该拒），但报错文案指向「不一致」，会让人误以为是数据问题。

### P2-5 DETAIL 结果行序不稳定（03 遗留）

Q4 返回 `江苏/上海/浙江`、Q5 返回 `机械键盘/4K显示器`，与期望表的字典序不同，两轮之间顺序也会变。**06b 的行级对拍必须用集合比对**，否则会误报 2 条 FAIL（我第一版探针就是这么误判的）。

### P2-6 跨表字段仍穿透五道闸门（03 P1-2 遗留）

`gmv_total`（交易表）+ 维度 `channel_name` / 过滤 `region`：`存在性=PASS 权限=PASS 代价=PASS 语法=PASS`，SQL 发到库才报 `Unknown column`，`answer` 全文吐 `BadSqlGrammarException`。04 没有让它更糟，但「窗口 + 跨表」这组新组合同样穿透。

### P2-7 verify_stub_ir.py 的健壮性

遇到违规桩直接 `assert` 抛出终止（第一个就崩），不会继续收集其余文件的同类问题；文件名必须是 `q<整数>.json`，我放 `q98_bad_anchor.json` 时脚本 `int()` 直接崩。

## 六、修复建议（按优先级）

1. **补空问题兜底**（P1-1）：`extractQuestion` 取到空白时返回 `""`、Engine 入口对 blank question 直接短路返回「无法识别」，别再回落整段 prompt。这是唯一能产生静默错答案的入口，成本很低。
2. **把「窗口题必须断言 SQL 形状」写进 06b**（P1-2）：值对拍在这批数据上判不出半开/闭区间；同时保留 days=3 探针作为回归项（157702.85 vs 223887.35）。
3. `relativeWindow == null` 改为显式拒绝或至少打 warn（P2-1），让注释与行为一致。
4. `anchors.get(table, this::loadAnchor)` 换成原子读（P2-2）；锚点 DataSource 可复用引擎侧连接配置，避免每次新建连接。
5. TTL 挪进 `gate_config`（P2-3），或至少在 `application.yml` 里可配。
6. 06b 的行级对拍统一用**集合比对**（P2-5），DETAIL 题不要按顺序判定。
7. 跨表字段校验（P2-6）建议在存在性闸门里补 `table.field` 作用域判断（`OntologyCache.tableFields()` 已存在但全仓无人调用），这是 02/03 留到现在的同一处洞。
