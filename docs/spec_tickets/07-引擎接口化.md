**关键实现决定**
1. **接口只留一个执行入口**：`query(String)` 保留只是接口兼容与运维自检，主链路（`SqlExecuteStep`）只调 `query(SqlCommand)`。裸字符串入口天生无法保证参数化，一旦被主链路用上，参数化绑定的红利就没了。
2. **白名单钩子不做死代码**（吸取 QA-05 P2-3「`braces()` 成了死代码」的教训）：`readableTables()` 由 `EngineWhitelist` 真实消费——启动自检 + `GET /api/health/engine` 暴露。**只自检、不拦截**，拒绝判定仍归 Ticket 02 的存在性与权限闸门（票面「实际注册逻辑在 Ticket 02 内完成」）。
3. **写错配置要炸在启动期**：`type=mysqll` 时两个 `@ConditionalOnProperty` 都不匹配 → 容器里没有 `SqlExecutor`，**真实链路**是 `agentEngine → recallStep → timeAnchorProvider → engineJdbc` 依次构造（`TimeAnchorProvider` 也依赖 `EngineJdbc`，比 `SqlExecuteStep` 更早），最终报错落在最末 `Caused by`。现在 `EngineJdbc` 构造直接抛「不受支持，可选值：[mysql, starrocks]」，**报错点比交付初稿说的「注入 `SqlExecuteStep` 处」更早一层**（QA-07 P2-6 纠正）。
4. **`EngineJdbc` 继续不声明为 `DataSource` 类型**：一旦容器出现第二个 `DataSource` bean，Boot 的 `DataSourceAutoConfiguration`（`@ConditionalOnMissingBean(DataSource.class)`）整体退让，`MetadataRepository` 会连到业务库去（Ticket 04 踩过）。
5. **MySQL 侧连接仍设 `readOnly=true`**：票面明确不承诺 MySQL 侧只读（root/root123 是读写账号），但应用层这道保险不省，成本为零。

**本轮实测发现并修复的缺陷（P1 级，Ticket 04 遗留）**
- **现象**：切 MySQL 引擎问「演示库近7天的订单数」，用户拿到的文案是
  `无法从表 orders 读取 MAX(dt)（列不存在或引擎不可用）：StatementCallback; bad SQL grammar [SELECT MAX(dt) AS m FROM orders]`
  —— `BadSqlGrammarException` 原文（含 SQL 片段、表名、驱动措辞）**直接漏给最终用户**，与 QA-03 P1-2「只回 traceId、原文进日志」的口径冲突。
- **根因**：`TimeAnchorProvider.loadAnchor` 的 catch 把 `e.getMessage()` 拼进 `IllegalArgumentException`，`AgentEngine:109-111` 又把 `e.getMessage()` 原样当 `answer`。
- **修复**：message 只保留「表 X 读不到时间字段 dt（列不存在或引擎不可用），无法确定近 N 天窗口的结束日 + 可执行下一步」，原文与异常类名只进 `log.warn`。已加 `TimeAnchorProviderTest.dbErrorTextNeverReachesUserMessage` 钉死（断言 message 不含 `SELECT` / `MAX` / `BadSqlGrammar`）。
- **为什么 07 才暴露**：StarRocks 侧四张 ADS 表都有 `dt`，这条 catch 分支自 Ticket 04 起从未被真实触发；MySQL 演示库 `orders` 没有 `dt`，一启用时间窗口必踩。

### 复核确认

| 项 | 评审方实测（修前） | 07b 后 |
|---|---|---|
| `consistent` 语义 | 真切 MySQL：`declared=[orders]`、`metadataNotDeclared=[4 张 ADS]`、**`consistent=true`** —— 最危险方向的失配被报成一致 | 双向判据，此场景 `false` |
| `--datapilot.engine.type=`（留空） | 报 `type= 不受支持，可选值：[starrocks, mysql]`，且文案不提「不填默认 starrocks」；真删掉 yml 那行起不来 | 空/空白归一 `starrocks`，与 `matchIfMissing=true` 对齐；非法值文案补「留空默认 starrocks」 |

### 我的测试为什么没抓到（覆盖缺口，已补）

`reportShowsBothDirectionsOfMismatch` 构造的是**双向同时失配**，`declaredNotInMetadata` 本来就非空，旧的单向判据 `declaredNotInMetadata.isEmpty()` 会返回 `false` —— **用例名说双向，实际只验了「至少一个方向」**。真实切换场景恰恰是另一侧单独非空。07b 补 `reportIsInconsistentWhenMetadataHasTablesEngineCannotSee`（`declared ⊂ metadata`，只有 `metadataNotDeclared` 非空），变异 M3 验红。

教训记这里：**「双向」的用例必须把两个方向各拆一条独立用例**，否则永远是弱的那一侧在测。

### 未接线（不属于本票，已挂 AC）

评审方观察：同一 MySQL 场景下问 ADS 问题，**四道闸门全 PASS，到 DB 层才报错**。原因是闸门③（存在性）只查 `OntologyCache.tables()`（元数据白名单 = 4 张 ADS），不看引擎侧声明；`EngineWhitelist.effective()`（`declared ∩ metadata`，此时为 ∅）至今没有消费方。

这不是「数错」而是「错误暴露得太晚」，且根因是**语义层与执行引擎没有绑定**（元数据白名单是全局一份，切引擎后仍指 StarRocks 的表），属于多数据源语义层问题，不走 07 的收口。已作为验收项写入 `02-五道闸门与维度字典一对多.md`：闸门③ 判表可读时必须用 `EngineWhitelist.isReadable()`，`effective` 为空要在 IR 层拒绝并给可执行文案（「当前引擎 mysql 无可读表，请检查语义层与 datapilot.engine.type 是否匹配」），而不是放行到 JDBC。
