# Ticket 19：「加表零改动」缺口收口

## 目标
独立评审逐链路核源码后给出结论：**「加表和减表不需要改动代码」在问数主链路上成立，
但代码里有 4 处会让它不成立，其中 1 处是真硬编码。**
本票把这 4 处收掉（1 处真修、2 处补能力、1 处写清边界），并留下可复现的验收脚本。

## 背景
评审的原始判定（逐链路）：

| 链路 | 需要改代码 | 依据 |
|---|---|---|
| 闸门①存在性 / ②权限 | 不需要 | 只读 `OntologyCache`，事件驱动刷新 |
| 闸门③语法 | 不需要 | 同一份缓存二次比对 |
| SQL 生成 | 不需要 | 表名取自 `metric.getTableName()` |
| 意图召回 | 不需要 | `repo.listTables()` 动态取全量 |
| 前端元数据页 | 不需要 | 全由 API 渲染 |
| **引擎白名单自检** | **需要（真硬编码）** | 缺口 1 |
| 经营大屏 | 需要（设计如此） | 缺口 2 |
| 元数据写入 | 无接口，需手工写库 | 缺口 3 |
| 新环境重建 | seed 不覆盖新增表 | 缺口 4 |

## 任务

### 缺口 1（P1，真硬编码）
`StarRocksSqlExecutor.DECLARED` 写死 4 张 ADS 表 → 加第 5 张后 `EngineWhitelist.effective()` 交集永远缺它，
`GET /api/health/engine` 立刻 `consistent=false` + 启动 warn。它不拦问数，但会让人误以为链路坏了、
反过来去改代码。

- `DECLARED` 改为 `List.of()`（语义：引擎不额外限制，纯元数据说了算）。
- 修 `EngineWhitelist.report()` 的连带 bug：原来无条件 `metadata - declared`，`declared` 为空时
  它等于全部元数据 → `consistent` 恒 `false` + 4 条 warn。现在未声明时该差集为空，
  并新增 `declarationMode`（`metadata-only` / `declared`）。
- 启动日志增加一行说明「未声明 ≠ 漏配」，指向 `/api/health/drift` 做物理一致性。

### 缺口 3（P2，能力缺口）
- `MetadataRepository`：`findTable` / `deleteTable` / `countFieldsOfTable` /
  `metricIdsUsingTable` / `metricIdsUsingTableAsDenominator` / `dimensionNamesOfTable` /
  `metricTableRefs`。
- `MetadataService.putTable(m, createOnly)`：表名格式校验、`createOnly` 已存在 → 409、发 `MetadataChangedEvent`。
- `MetadataService.deleteTable(t)`：**五道守卫**逐条查，任一命中 400 并点名引用方，**不做级联删除**
  （字段白名单 / `metric_def.table_name` / `denominator_table` / `dimension_def` / `metric_table`）。
- `MetadataController`：`PUT /api/metadata/tables`（`mode=create|upsert`）、`DELETE /api/metadata/tables`。
  鉴权沿用 `/api/metadata/**` 的 admin+dba 规则，`write-enabled=false` 时 403。
- 前端：元数据页表卡片加「新增表」按钮（弹窗三项）+ 每行「注销」（`Popconfirm`，`stopPropagation`）。

### 缺口 4（P3，可复现性）
- 新增 `qa/dump_metadata.py`：从活库导出 semantic_model / field_metadata / metric_def / gate_config
  为幂等 SQL（`-o deploy/seed_from_live.sql`）。
- 澄清一个误判：`seed.sql` 对表/字段是 `INSERT IGNORE`（只补缺、不删新增），
  **「重跑 seed 会清空新表」不成立**；真问题是 seed 不反映实况。

### 缺口 2（P2，边界而非缺陷）
大屏是固定口径视图（`DashboardService` 四个 `mall_dw.ads_*` 常量 + 写死列名），
不随元数据变化。**写进文档**，防止下次拿「加表零改动」验收大屏导致误判。

## 偏差与踩坑（如实记录）

1. **端到端只覆盖了「字段守卫」**：`metric_def` / `dimension_def` / `metric_table` 三类引用需要
   「无字段但被指标引用」的表才能构造，而删指标没有接口（只能改回），会把真实元数据搞脏。
   这三类由 `MetadataServiceTableTest` 单测覆盖，端到端不构造。
2. **`EngineSwitchTest` 有一条断言被改**：原来断 `readableTables()` 含 4 张 ADS 表，
   现在断 `isEmpty()`。这不是放宽，是语义变了 —— 从「写死清单」变成「不声明」，后者才是加表零改动的前提。
3. **`ads_trade_overview_di.dt` 的 `field_role` 活库是 `NULL`，seed 写的是 `dimension`**：
   导出时发现的历史漂移，本票未修（不属本票范围），记在文档里作为「导出比 seed 可信」的实证。
4. **`dimension_def` 仍无写接口**：新增业务维度还要手工写库。不影响加表主链路（能问数），
   影响「能按这个新维度问」。挂账。
5. **`deploy/dp-web/nginx.conf` 此前未入库**：P1 落地时这个文件只存在于 `D:/starrocks/dp-web/`，
   别人 clone 后 8080 起不来。本票随 Ticket 18 一并入库。
