### 2.3 「不用重启」是真的（缓存事件失效，不是靠 60s TTL）

这条是本票最容易「嘴上说达成就行」的地方，我用存在性闸门做了双向验证（同一 `previewId`，同一 IR，只动白名单）：

| 步骤 | 操作 | 存在性闸门 |
|---|---|---|
| ① | 把某题的维度字段改成 `zz_qa_gate_probe`（白名单里没有） | `存在性=REJECT`，文案 `维度字段不存在或超出可查询范围：zz_qa_gate_probe` |
| ② | 页面同款 `PUT /api/metadata/fields` 加进白名单 | 同一 IR **立刻** `存在性=PASS`（随后被语法/执行阶段拦，与白名单无关） |
| ③ | `DELETE` 把它移出 | 同一 IR **立刻** 回到 `存在性=REJECT` |

②③ 之间没有任何等待，`OntologyCache` 的 TTL 是 60s —— 说明生效路径是 `MetadataChangedEvent → cache.invalidateAll()`，不是等过期。顺带证了反向：`paid_order_cnt` 被删后 q2/q9 立刻坏、恢复后立刻好（见 §3.3 J 段）。

## 6. 修复建议

1. **P2-1 补齐删除守卫**：`deleteField` 在查 `dimension_def` 与 `metric_def.dimensions` 之外，再查 `metric_def.metric_sql` 与 `denominator_sql` 的列引用。做法建议在 Java 侧取出候选 `metric_id` 列表后逐条比对**已解析的列名集合**，而不是 `LIKE '%paid_order_cnt%'` —— `dt` 会命中 `create_dt`，这正是仓库里已经在 `dimensions` 上用 `FIND_IN_SET` 规避过的同类坑。命中则 400 并点名 `metric_id`。

2. **P2-2 区分创建与覆盖**：页面「新增字段」保存前先按 `tableName+fieldName` 查一次白名单，命中就提示「该字段已在白名单里，要改请用编辑」，或后端加 `mode=create` 时对已存在键返回 409。**不要**在页面只做前端校验就算完 —— 覆盖的语义必须由接口决定，这条与 QA-08「空值 = 默认值由装配侧决定」是同一个教训。

3. **P3-2/P3-3 一起改**：`PUT /api/gate-config` 的入参只保留 `paramKey/paramValue/updatedBy`（`gateName` 由服务端派生，去掉 `@NotBlank`），返回落库后的整行（含 `update_time`），页面就不必靠 `load()` 兜。

4. **P3-5/P3-6 前端两处小修**：抽屉重建 `dimensions` 时保留 `d.alias`；`limit` 的 `max` 从 `/api/gate-config` 的 `max_limit` 取，别写死 5000。

5. **P3-7 把 `qa13_ui.cjs` 的两条正向保存并入 `qa/smoke_frontend.cjs`**（指标页编辑保存、闸门页改阈值保存），这样 `npm run build` 之后一条命令就能覆盖四页的可操作性。

## 7. 结论

Ticket 13 的四页面与后端补口，在 `92b2e61` 固定副本上**全部达成票面要求**：问数页左结论右证据、参数化在页面上看得见（SQL 只有 `?`，`15604.97` 在 `params`）、HITL 两段接进交互且改值真改了结果（15604.97 → 20324.53）、白名单增删不用改代码不用重启（事件失效，不是等 TTL）、写开关关闭时页面与接口表现一致。
