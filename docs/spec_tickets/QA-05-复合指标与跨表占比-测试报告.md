## 4. 缺陷清单

### P0
无。

### P1
无。数值层没有静默错：15 题 + 10 个对抗用例，凡是出了数的都对，凡是口径不成立的都显式拒绝（拒绝文案有一处归因错，见 P2-2）。

### P2

**P2-1 空结果提示被闸门链吞掉，用户看到的是无提示的空表**
位置：`agent/gate/GateChain.java:runPhase`（第 42-51 行）+ `agent/gate/ResultCheckGate.java:check`（第 44-47 行）
`ResultCheckGate` 对空结果返回 `okWarning("无数据：查询结果为空，请检查筛选条件")`，但 `runPhase` 只在 `!r.isPass()` 时返回该结果，通过时一律 `return GateResult.ok()`，warning 被丢弃。`AgentEngine` 第 ⑨ 步的 `resultGate.getWarning() != null` 因此永远为 false。实测 Q15 用一个无数据日期：`rows=[]`、`answer=''`、`结果自检=PASS`。
影响：不是数值错，但没有数据时前端只能靠 `rows` 为空自行兜底，闸门宣称的「包装成可读反馈」实际未生效。若前端不判空，应升 P1。
归因：Ticket 02 遗留，Ticket 05 的占比用例第一次构造出真正的 0 行结果（此前 `SUM` 无数据返回 1 行 null，走不到该分支）。

**P2-2 旧 `ratio` 字段的拒绝文案指错方向**
位置：`agent/gate/ExistenceGate.java:104-111` 与 `sql/IrToSqlConverter.java:106-112` 的顺序冲突
`ExistenceGate` 在 IR 阶段先校验 `ir.ratio.numerator/denominator` 是否为真实指标，命中不存在就直接返回「占比分子/分母指标不存在或超出可查询范围：gmv」；`IrToSqlConverter` 里那段「占比语义请改用复合指标（Ticket 05）」的文案因此不可达（只有当 ratio 的分子分母恰好都是合法 metricId 时才会走到）。
影响：同样是显式拒绝、不会算错，但把「写法已停用」误导成「指标不存在」，用户会去查指标名而不是改写法。
建议：`ExistenceGate` 的 ratio 分支改为直接拒绝并给出 Ticket 05 的文案，或整段删除、把该判断收进 converter。

**P2-3 写入口径正则比生成器更严，`braces()` 成了死代码**
位置：`service/MetadataService.java:29-31`（`AGG_PATTERN` / `RATIO_PATTERN`）vs `sql/IrToSqlConverter.java:307-313`（`braces`）
实测 `(SUM(paid_order_cnt))/(SUM(visit_uv))` 被 PUT 400 拒绝（「metric_sql 非法」），而 `braces()` 的注释明确写着「防止元数据里多写一层括号导致后续判断走偏」。两侧契约不一致：生成器兼容的写法写不进库，只有直接改库才可能用到该分支。
影响：不影响现有 13 个指标，但会让「生成器支持什么」和「元数据允许什么」长期分叉，06b 造测试数据时会踩。
建议：二选一 —— 要么 `RATIO_PATTERN` 允许一层外括号，要么删掉 `braces()` 并在文档里写明「口径禁止外括号」。

**P2-4 代价闸门不统计跨表占比的分母表**
位置：`agent/gate/CostGate.java:54-64`
`joinCount` 只把 `metrics` 的 `table_name` 去重，`gmv_channel_ratio` 实际读 `ads_channel_conversion_di` + `ads_trade_overview_di` 两张表，但 `joinCount = 0`。存在性闸门和权限闸门都已补了分母表（`OntologyCache.metricDenominatorTables()`），代价闸门没补，三个闸门覆盖不一致。
影响：当前单指标单分母，`max_join=1` 打不穿；但 Ticket 15「代价公式补洞」若不修，跨表占比可以绕过 join 上限，而且闸门回显的「代价=PASS」是虚假的安全感。
建议：`CostGate` 把 `cache.metricDenominatorTables()` 的表也加进去重集合。

**P2-5 元数据写入不校验分母表/字段真的存在**
位置：`service/MetadataService.java:121-151`（`validateRatioConfig`）
`denominator_table=ghost_table` 与 `denominator_sql=SUM(gmv)`（gmv 不属于 trade 表）都是 **HTTP 200 落库**，直到查询时才被存在性闸门/生成器拦住。库内因此可以存「永远查不通」的指标，而且写入方拿到 200 以为成功了。
影响：与 QA-01b 的 P0-2 同源（写时零校验、读时才炸），本票只补了格式与成对性，没补存在性。
建议：`validateRatioConfig` 增加「分母表在 `semantic_model` 白名单」「分母字段在 `field_metadata` 且属于该表」两项校验，直接 400。

**P2-6 seed 幂等但不收敛**
位置：`deploy/seed.sql`（只有 `pay_conversion_rate` 有显式 `UPDATE`）
实测把 `gmv_channel_ratio` 的 `denominator_table/denominator_sql` 改坏后再跑 seed，值**不会**被拉回基线（`INSERT IGNORE` 跳过既有行）；`pay_conversion_rate` 因为有显式 UPDATE 会拉回。
影响：本地/CI 想用「重跑 seed」把元数据复位到基线是做不到的，只能重建库。交付里「补了显式 UPDATE 保证可重复执行」这句话只对 `pay_conversion_rate` 成立。
建议：把 13 条指标的 `metric_sql/metric_type/table_name/denominator_*` 全部用 `INSERT ... ON DUPLICATE KEY UPDATE`，或在 seed 头部写明「只补缺不纠错，复位请重建库」。

**P2-7 迁移脚本硬编码 `USE data_agent`**
位置：`deploy/migrate/V05_metric_def_denominator.sql:9`（以及第 13/21/30 行的 `TABLE_SCHEMA = 'data_agent'`）
脚本无法参数化，在隔离库/CI 上直接跑会**作用到 `data_agent`**（本次测试必须 `sed` 改库名才能安全执行）。另外脚本只负责加列，不回填历史口径 —— 老库若只跑迁移不重跑 seed，`pay_conversion_rate` 仍是裸列名（`isComposite` 判为 false，生成器直接吐裸列）。
影响：运维顺序敏感，容易「迁移跑成功但功能没生效」。
