## 4. 缺陷清单

### P0 / P1
无。

### P2

**P2-1｜`consistent` 只判单向：元数据指向引擎没有的表（更危险的方向）仍报 `consistent=true`**

- 位置：`knowledge/EngineWhitelist.report()` → `out.put("consistent", declaredNotInMetadata.isEmpty())`
- 实测（18094，engine=mysql）：`declared=[orders]`、`metadata=[4 张 ADS + orders]`、`metadataNotDeclared=[4 张 ADS]`、`consistent=true`
- 影响：切到 MySQL 后元数据还指着 4 张 StarRocks 表，这是**明确的失配状态**，接口却报一致。运维按 `consistent` 做告警会漏掉；随后用户问一句才在 DB 层报「SQL 执行失败」（B3 实测），违反「提前暴露而不是等用户问」的设计初衷。交付里把 `consistent=true` 当成「自检正确」，其实是字段语义被写窄了。
- 旁证：`EngineWhitelistTest.reportShowsBothDirectionsOfMismatch` 自己断言「双向失配 → `consistent=false`」，说明作者对 `consistent` 的理解是「两个方向都空」。但用例构造的是双向失配（declared 里也有 metadata 没有的表），**没有覆盖「只有 metadataNotDeclared 非空」这个真实切换场景**，所以测试没能发现。

**P2-2｜「缺省即 starrocks」不成立，`matchIfMissing` 与 `EngineJdbc` 的空值校验互相矛盾**

- `StarRocksSqlExecutor` 标 `matchIfMissing=true`（注释与 07 票面都说「缺省即 starrocks」），但 `EngineJdbc` 构造对 `type` 做了 `SUPPORTED.contains(type)`，null/空一律抛 `不受支持`。
- 实测 `--datapilot.engine.type=` → `IllegalStateException: datapilot.engine.type= 不受支持，可选值：[starrocks, mysql]`。也就是说：属性**缺失**时 `@ConditionalOnProperty` 会装 StarRocks（按 matchIfMissing），但 `EngineJdbc` 会先炸，应用起不来。当前 yml 显式写了 `type: starrocks`，所以线上不受影响；一旦有人删掉那行（yml 注释里正在鼓励「切引擎只改这三行」），报错文案是「type= 不受支持」，而不是「不填默认 starrocks」，排查会绕一圈。
- 旁证：`EngineSwitchTest.defaultIsStarRocksAndItIsTheOnlyExecutor` 名叫 default，实际显式传了 `type=starrocks`，**这条用例没有验证缺省**。

**P2-3｜白名单钩子三个入口里有三个没有业务调用方**

- `SqlExecutor.query(String)`：全仓只有测试调用（注释写「只给运维/自检」），但 `EngineWhitelist` 与 `HealthController` 都没用它。
- `SqlExecutor.listTables()`：无业务调用方（交付「已知遗留」已披露，留给 Ticket 16）。
- `EngineWhitelist.isReadable()`：除单测外无调用方（交付说「留给 Ticket 02 接线」）。
- 结论：钩子的**真实**消费方只有 `report()`（启动日志 + 健康检查），这部分是活的；另外三个入口目前是待接线状态，不算缺陷，但和「不做死代码」的自我要求之间有张力，建议在票面里把「谁会用、什么时候接」写死，避免拖到 16 之后又被当成死代码清掉。

**P2-4｜`SqlCommand.of(sql, null)` 会让 `query(SqlCommand)` 抛 NPE**

- 位置：`JdbcSqlExecutor.query(SqlCommand)` → `cmd.params().toArray()`；只挡了 `cmd == null`，没挡 `params == null`。
- 现状：主链路 `IrToSqlConverter` 恒传非空 List，所以打不到；但接口是 public 的，别的执行器（Excel/DuckDB）实现时容易踩。加一行 `cmd.params() == null ? new Object[0] : …` 或 `List.of()` 归一即可。

**P2-5｜`EngineSwitchTest` 的 MySQL 真跑断言偏弱**

- `mysqlEngineRunsSingleTableQueryOnOrders` 只断言 `cnt >= 0`，等于「表在、查询不报错」；5 行是端到端手测出来的（本报告 B1 也复现了 5），单测没有断言具体值。
- 建议：`orders` 在 `schema.sql` 里是空表（仓库不 seed 业务数据），单测可以只断言 `>=0`；但至少再加一条 `SELECT 1 AS v` 之外的「列名正确」断言，避免 `cnt` 这一列被别名改坏时静默通过。

**P2-6｜交付里 fail-fast 的报错位置描述不准**

- 交付写「报错点会在注入 `SqlExecuteStep` 处」。实测链路是 `agentEngine → recallStep → timeAnchorProvider → engineJdbc`，因为 `TimeAnchorProvider` 也依赖 `EngineJdbc`，且它在 `SqlExecuteStep` 之前构造。真因仍出现在最末 `Caused by`，fail-fast 的目标达到了，只是位置比描述更早一层，写进记录避免后来人对不上。

## 6. 修复建议

1. **P2-1（最该修）**：`consistent` 改成 `declaredNotInMetadata.isEmpty() && metadataNotDeclared.isEmpty()`；补一条测试「declared ⊂ metadata，仅 metadataNotDeclared 非空 → consistent=false」。这样切 MySQL 时健康检查会直接报红，不用等用户问一句才发现元数据还指着 StarRocks。如果担心 `metadataNotDeclared` 在「元数据故意多于当前引擎」时误报，就把它拆成两个字段（`declaredMissingInMetadata` / `metadataMissingInEngine`），别用一个布尔混装两种语义。
2. **P2-2**：`EngineJdbc` 里把空值归一成 `starrocks`（`type == null || blank ? "starrocks" : type`），与 `matchIfMissing=true` 对齐；或者反过来把 `matchIfMissing` 删掉、yml 写死必填，二者选一，别留两套「默认值」定义。顺手把 `defaultIsStarRocksAndItIsTheOnlyExecutor` 改成真的不传 `type`。
3. **P2-4**：`query(SqlCommand)` 前把 `params` 归一成空 List，一处改动。
4. **P2-5**：补一条列名断言（`rows.get(0).containsKey("cnt")` 已有，可再加「列数 = 1」）。
5. **P2-6**：把落地记录里「报错点会在注入 SqlExecuteStep 处」改成「会在 `TimeAnchorProvider` 构造链上炸，最末 Caused by 是真因」。
6. **P2-3**：在 02 / 16 的票面里各写一句「`isReadable()` 由存在性闸门消费」「`listTables()` 由语义模型巡检消费」，避免三个待接线入口被当成死代码删掉。
