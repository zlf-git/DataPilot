## 2. 三个 `max(1,·)`，不止维度一个

票面只写了「维度数 max(1,·)」，实测发现**同一个洞还有两个入口**，一并堵了（见第 5 节偏差 1）：

- **join=0（单表）**：Q1/Q2/Q9 都是单表，join 因子 0 → 乘积照样 0。跨表占比（2 表）才是 1。
- **指标=0（DETAIL 明细题）**：Q4「华东地区有哪些省份」是 `selectMode=DETAIL`、metrics 为空，指标因子 0 → 乘积 0。

三个因子各取 `max(1,·)` 后，最简查询得分 1；「多一维/多一表」才真的加分。留任何一个裸因子，补洞就是纸糊的。

## 3. 阈值语义：`≥` 而不是 `>`，默认 3

- 票面验收要求「**阈值=1 时能拦**」。若用 `>`，阈值 1 的含义是「允许复杂度 1」，最简查询正是 1，照样放行 —— 补洞白做。
  所以比较写成 `complexity >= max_complexity`，`max_complexity` 是**拒绝点**，不是「允许上限」。
- 默认 3：当前能力（`max_metric=1`、`max_join=1`）下最重的一题是跨表占比（2 张表）= 1×1×1 = 1，默认值不误杀；
  等维度或表数放开，分值自然逼近 3。没有像早期那样直接配 3/2 导致「阈值永远不可达」（QA-03 P2-5 的教训）。
- 老库没有这一行时，闸门走代码默认 3 —— 配置缺失不炸，脚本 ① 段专门锁了这一条。

## 5. 票面偏差（3 条）

1. **公式从「max(1,维度数)」扩到三因子各自 max(1,·)。** 原因见第 2 节：只堵维度这一个乘数，单表题（join=0）和明细题（指标=0）照样恒通过。
   票面验收点名的是 Q1/Q2/Q9/Q14，其中 Q9 是**同表复合、无维度**，Q4 是明细题 —— 只按票面字面实现，这四题的洞只堵住一半。
2. **新增了一个 `gate_config` 键 `max_complexity`（票面没提）。** 票面只说「改复杂度公式」，但验收要求「阈值=1 时能拦」，
   没有阈值这个参数根本无从「设 1」。因此按既有 `gate_config` 机制加键（默认 3），并补 seed + 迁移 + 闸门页说明。
3. **默认值取 3，不取票面暗示的「1 才能拦」。** 阈值=1 是把闸门关死（连「当天总 GMV」都拒），只能当验收探针，不能当默认值。

## 6. 已知边界

- **复杂度是静态预估，不是真实代价**：公式只看 IR 形状（指标数/维度数/表数），不看数据量、谓词选择性、是否命中分区裁剪。
  同一条 SQL 在 75 行和 7500 万行上分值一样 —— 它挡的是「LLM 拼出笛卡尔积」这类结构性风险，不是性能调优。
- **维度按 IR 的 dimensions 长度算**：DETAIL 与 AGG 都只数条数，不区分「同一字段重复写两次」这种退化情况（生成器侧已去重，见 QA-12）。
- **`max_complexity` 与 `max_metric`/`max_join` 有重叠**：三条硬上限仍在前，复杂度阈值是它们之上的第二道。
  所以把 `max_complexity` 调大而 `max_metric` 不放开，实际放不出多指标查询 —— 这是有意的（硬上限管能力，复杂度阈值管形状）。
