## 二、功能测试明细（24 次请求）

契约与主链路：traceId 32 位无横线且每次唯一；gates=[] / chartType=table / reportHtml="" 与占位约定一致；costMs 39ms，墙钟 98ms（首包含冷启动），后续 30-40ms；IR 回显完整（metrics[gmv_total] / filters[dt,EQ,2026-10-19] / limit=null）。

异常兜底（全部 200，无 500）：空字符串、question=null、缺 question、空对象均走兜底文案；非法 JSON 与空 body 返回 400；2000 字符长问题、`<script>alert(1)</script>`、多行指令注入均 200 无异常。

文本注入防护（正面结论）：问题文本塞 `10月19日总GMV是多少'; DROP TABLE x; --` 仍返回 200 与 53042.41。metric_sql 取自 metric_def 而非 LLM 输出，问题文本不进 SQL，该通道干净。

并发：10 线程同题并发全部 200，traceId 10/10 唯一，结果集恒定，耗时 69-112ms。

## 四、P0 安全窗口（属 Ticket 02，非本票缺陷）

IrToSqlConverter.buildCondition 中 value 已参数化，但 `f.getField()` 直接拼接进 SQL，来自 LLM 输出的 IR 字段未做任何白名单校验，SqlValidateStep 为空实现。存在列位注入面，value 参数化无法覆盖列名拼接。桩模式下 field 固定为 dt 暂无害；结论是该窗口落地前不得把 provider 切 deepseek 跑真实流量。

## 五、桩匹配边界（影响 Ticket 01c）

StubLlmClient 用 `userPrompt.contains(question)` 精确子串匹配，实测：

| 问法 | 命中 |
|---|---|
| 10月19日总GMV是多少 | 命中 |
| 10月19日总GMV是多少？（带标点） | 命中 |
| 10月19日总GMV是多少 + 尾空格 | 命中 |
| 10月19号总GMV是多少（号/日差异） | 未命中 |
| 10月19日 总GMV 是多少（多空格） | 未命中 |
| 总GMV是多少（缺日期） | 未命中 |

01c 补 15 条 stub_ir 时，每条仅能命中与 json 内 question 字符串完全同文的问法；06b 评测若换措辞会全线报「无法识别查询意图」，易被误判为 L1 槽位错。建议匹配前做归一化（去空格标点、号→日），或保证 stub question 与评测集原题逐字一致。
