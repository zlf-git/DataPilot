# DataPilot 五道闸门（F-04 安全兜底）

| 项 | 内容 |
|---|---|
| 文档版本 | v1.1 |
| 更新日期 | 2026-10-20 |
| 作者 | 张灵枫 |
| 关联文档 | IR_Schema.md（F-02）、Prompt模板.md（F-03） |

> 五道闸门是「LLM 生成 SQL」这条路径的硬兜底：Prompt 只能软约束 LLM，闸门在 IR 层、SQL 层、结果层三级拦截，保证即使 LLM 出现幻觉也不会造成越权、注入、拖垮集群。执行顺序如下。

## 执行链路与闸门位置

```
自然语言 → 召回 → Prompt → LLM 生成 IR
   → [闸门1 存在性] → [闸门2 权限] → [闸门3 代价]
   → IR 转 SQL → [闸门4 语法]
   → 执行(只读账号) → [闸门5 结果自检] → 返回
```

---

## 闸门 1：存在性闸门（IR 层，最先）

**职责**：确保 IR 中每个表、字段、指标都真实存在于 Ontology 白名单，把 LLM 幻觉率压到 0。

| 项 | 内容 |
|---|---|
| 校验对象 | IR 的 `table` / `field` / `metricId` |
| 校验规则 | 表 ∈ 4 张 ADS 表白名单；字段 ∈ 字段白名单；指标 ∈ `metric_def` 白名单 |
| 实现 | 白名单加载进 `HashSet`，O(1) 查找；字段按 `table.field` 复合键校验 |
| 违例处理 | 拒绝执行，返回「问题超出可查询范围」 |

**拦截示例**：LLM 幻觉生成字段 `total_sales`、表 `dwd_trade_order_detail`（文档假设表，真实环境不存在）→ 直接拦截，不会带到 SQL 层。

---

## 闸门 2：权限闸门（IR 层）

**职责**：只允许读，且只允许读白名单内的表；执行账号本身也只读，双保险。

| 项 | 内容 |
|---|---|
| 校验对象 | IR 涉及的表 + 执行账号 |
| 校验规则 | 表 ∈ 只读表白名单（4 张 ADS）；执行账号无写权限 |
| 实现 | 执行固定用 StarRocks 只读账号 `agent_ro`（仅 SELECT 授权）；IR 本身不含写语义 |
| 违例处理 | 越权表拒绝；写操作在账号层直接报权限错误 |

**双保险**：① IR 层校验表白名单；② 账号层 `agent_ro` 连 UPDATE/INSERT/DELETE 权限都没有，即便某层漏过，写入也会被数据库拒绝。

---

## 闸门 3：代价闸门（IR 层）

**职责**：预估查询复杂度，防止 LLM 生成全表扫描、多表笛卡尔积等拖垮集群的查询。

| 项 | 内容 |
|---|---|
| 校验对象 | IR 的指标数、维度数、join 表数、limit、复杂度分值 |
| 校验规则 | ① 硬性上限（读 `gate_config`：`max_metric`、`max_join`、`max_limit`）；② 复杂度分值 = `max(1,指标数) × max(1,维度数) × max(1,join数)`，**分值 ≥ `max_complexity` 即拒绝** |
| 实现 | 从 IR + 元数据直接计算，无成本即可预估 |
| 违例处理 | 超阈值拒绝，返回「查询过于复杂 / 复杂度过高（含三因子原值），请拆分问题」 |

**三因子为什么各自 `max(1,·)`**（Ticket 15 / 审计 P1#19）：原式 指标数 × 维度数 × join 数 里只要有一个因子是 0，乘积就是 0 —— 「10月19日当天总 GMV」这类最常见的单指标单表题维度=0、join=0，复杂度恒 0，阈值调多紧都拦不住。三个下限 1 之后，最简查询得 1，复杂度从「可能为 0 的乘积」变成「相对基线 1 的倍数」：多一个维度、多一张表就真的加分。DETAIL 明细题没有指标（指标数=0），同样靠指标因子的 `max(1,·)` 兜住，否则明细题会成为第二个恒通过的口子。

**阈值语义是「拒绝点」不是「允许上限」**：比较用 `≥` 而非 `>`。验收要求「阈值=1 时能拦住维度=0 的题」，若用 `>`，阈值 1 的含义变成「允许复杂度 1」，最简查询照样放行，补洞等于没补。默认值 3：当前能力（单指标、单 join）下最重的一题（跨表占比，2 张表）= 1×1×1 = 1，不会被误杀；维度或表数再放开时分值自然逼近 3。

**join 表数必须含分母表**（QA-05 P2-4）：`gmv_channel_ratio` 实际读 `ads_channel_conversion_di`（分子）+ `ads_trade_overview_di`（分母）两张表，若只数 `metric_def.table_name` 会得出 `joinCount=0`，`max_join` 对复合指标形同虚设，闸门回显的「代价=PASS」是虚假安全感。同表分母（`denominator_table == table_name`）在去重集合里自然合并，不算一次 join。

**示例**：LLM 想把 4 张表全 join 起来（join 表数 = 4 > 1）→ 拦截；把 `max_complexity` 调到 1 → 连「10月19日当天总 GMV」（分值 1）都会被拦，这是验证补洞是否真生效的最快办法。

## 闸门 4：语法闸门（SQL 层）

**职责**：IR 转成 SQL 后，用 JSqlParser 解析校验语法合法性，并二次比对表/字段白名单（防 IR→SQL 转换引入非法引用）。

| 项 | 内容 |
|---|---|
| 校验对象 | 由 IR 生成的 SQL 字符串 |
| 校验规则 | `CCJSqlParserUtil.parse(sql)` 解析通过；解析出的表名/字段名 ⊆ 白名单 |
| 实现 | JSqlParser 提取 `TablesNamesFinder` 表名 + `Column` 字段名，与白名单比对 |
| 违例处理 | 解析失败或引用越权 → 拒绝执行 |

**双重价值**：① 语法合法性；② 即使 IR 层漏过，SQL 层的表/字段提取再次兜底，幻觉归零有第二道防线。

---

## 闸门 5：结果自检（结果层）

**职责**：对执行结果做合理性自检，把「无数据 / 异常值 / 超长结果」包装成可读反馈。

| 项 | 内容 |
|---|---|
| 校验对象 | SQL 执行结果集 |
| 校验规则 | 空结果 → 提示无数据；行数超阈值 → 截断；数值异常（如负 GMV、NULL 指标）→ 标记告警 |
| 实现 | 结果集元信息 + 抽样校验；告警信息随结果返回 |
| 违例处理 | 不拦截，但附告警说明，帮助用户判断结果可信度 |

**warning 如何真正到达用户**（QA-05 P2-1）：`GateChain.runPhase` 早先只在 `!isPass()` 时返回闸门结果，通过时一律 `return GateResult.ok()`，于是本闸门的 `okWarning(...)` 被丢掉，`AgentEngine` 第 ⑨ 步的 `getWarning() != null` 永远为 false —— 闸门宣称「包装成可读反馈」实际不生效，用户只看到一个空表。现在 `runPhase` 会收集本阶段所有 pass 闸门的 warning 合并返回（多条用 `；` 连接），`gateResults` 里也会标 `(WARN)`。

**示例**：查「某渠道某天 GMV」，结果为空 → 返回「2026-10-19 小程序渠道无数据」，而不是把空表直接抛给用户。

## 五道闸门总览

| 闸门 | 层 | 拦截什么 | 关键手段 |
|---|---|---|---|
| ① 存在性 | IR | 幻觉字段/表/指标 | Ontology 白名单 Set 查找 |
| ② 权限 | IR + 账号 | 越权/写操作 | 只读表 + `agent_ro` 只读账号 |
| ③ 代价 | IR | 大查询/笛卡尔积 | 复杂度公式 + 硬上限 |
| ④ 语法 | SQL | 语法错误 + 二次越权 | JSqlParser 解析 + 提取比对 |
| ⑤ 结果自检 | 结果 | 无数据/异常值 | 结果集元信息校验 |

**面试可讲的核心论点**：Text2SQL 的最大风险不是「SQL 写得慢」，而是「LLM 幻觉导致查错表、造字段、甚至拖垮集群」。五道闸门把生成空间收敛到白名单内，幻觉在 IR 层就被拦截，SQL 层再兜底一次，账号层只读三重保险——这是「语义层约束生成空间」技术路径区别于「裸调 LLM 生成 SQL」的关键。

## 闸门配置化与三级权限（v1.1）

### 1. 设计原则：机制硬编码，参数配置化

- **机制硬编码**：必须落白名单、必须只读、必须预检、必须 JSqlParser 校验——这些是安全逻辑本身，前端不可改。
- **参数/数据配置化**：白名单内容、join/limit 阈值、结果行数上限——这些是策略参数，前端可改。
- **反面红线**：若前端能「关掉校验」或「把 limit 调到无限」，等于把锁的钥匙交给被约束对象，安全机制形同虚设。

### 2. 配置落点

| 配置项 | 落点 | 可改角色 |
|---|---|---|
| 指标白名单 | `metric_def`（业务自助录入） | 业务部门 |
| 表/字段白名单 | Ontology 字段层定义（元数据管理页） | 元数据管理员 |
| 代价阈值（join≤N / 指标≤N / limit≤N） | `gate_config` | 平台管理员 |
| 结果自检阈值（行数上限 / 异常判定） | `gate_config` | 平台管理员 |
| `agent_ro` 只读授权 | StarRocks `GRANT` | DBA |

### 3. gate_config 表结构

| 字段 | 类型 | 说明 |
|---|---|---|
| gate_name | varchar | 闸门名（`cost_gate` / `result_gate`） |
| param_key | varchar | 参数名（`max_join` / `max_metric` / `max_limit` / `max_rows`） |
| param_value | varchar | 参数值 |
| updated_by | varchar | 修改人 |
| update_time | datetime | 修改时间 |

### 4. 前端「闸门配置」页

- 仅**管理员**可见，可调 `join≤2→3`、`limit≤1000→5000` 等策略参数。
- 业务用户无入口，进不来也看不到。

### 5. 三级权限分级

| 层 | 谁能改 | 改什么 |
|---|---|---|
| 业务层 | 业务部门 | 指标口径定义（`metric_def`） |
| 平台层 | 运维 / 平台管理员 | 闸门阈值（`gate_config`）、表/字段白名单 |
| 数据层 | DBA | `agent_ro` 只读授权（DB 层 GRANT） |

**结论**：业务自助定义「指标口径」（这是业务资产），但不能动「安全规则」（这是平台护栏）。指标是业务自己的事，闸门是平台保命的事——两层边界清晰，才能既让业务有自主权，又不被业务无意中击穿安全底线。
